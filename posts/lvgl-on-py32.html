64 KB 里做界面：
PY32 项目与 LVGL 的距离

LVGL 很轻，但“轻量”是相对于桌面浏览器而言，不是相对于一颗已经被业务占满的 64 KB MCU。

这次审查的对象是 PY32F003F18P6TU、ST7735S 160×80 横屏项目。现有功能已经包括 INA226 多地址扫描、NTC 测温、风扇控制、配置保存、低电量关机和一套自定义 UI。

先说结论

保留当前全部功能并直接接入完整 LVGL，不可行。删除现有 UI 后勉强裁剪，也仍然很紧，不值得作为产品路线。

先把资源账摊开

当前构建约为 39,000 B Code、8,572 B RO-data、388 B RW-data 和 4,836 B ZI-data。按 64 KB Flash 与 8 KB SRAM 计算，Flash 约剩 17 KB，SRAM 约剩 3 KB。

Flash47.96 KB / 64 KB
SRAM5.22 KB / 8 KB
全屏缓冲25.6 KB

LVGL 官方最低要求是 Flash 大于 64 KB、静态 RAM 约 2 KB，并且还需要显示缓冲和对象内存池。仅全屏 RGB565 缓冲就已经超过整颗芯片的 SRAM。

局部缓冲也救不了整个系统

使用 160 像素的一行缓冲只需要 320 B，但这只是画布的一部分。LVGL 自己的状态、对象树、样式、事件和定时器仍然需要空间。现有工程只剩约 3 KB，没有余量承担这些开销。

显示缓冲小，不等于 UI 框架的整体内存需求小。

现有自绘 UI 其实更合适

项目已经有差分槽、局部恢复、流式字符绘制和极简控件。对于固定页面和三个按键，这些定制的代价比完整控件系统更低。

如果以后要上 LVGL

  1. 换到至少 128 KB Flash、20 KB SRAM 的 MCU，舒适区间则是 256 KB Flash、64 KB SRAM。
  2. 保留 BSP、采集、配置和电源策略，只替换字体、绘制和控件层。
  3. 让 task 更新数据快照，UI 再更新控件，不要在中断里直接调用 LVGL。
  4. 按键映射到 `lv_group`，显示通过局部 `flush_cb` 发给 ST7735。

这不是“LVGL 不好”，而是工具和资源必须匹配。对当前设备，最合理的选择仍然是继续维护现有自绘 UI。
